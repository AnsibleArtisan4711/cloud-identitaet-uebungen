## Hinweise

- Alle Namen, Domänen und Werte sind erfunden (Domänen mit `.example`/`.test`). Alle Dateien liegen unter `/tmp/p28`. Die Ausgaben stammen vom Modell `entrasim.py`, nicht von Entra ID.
- Die Zeilen „az … ->“ sind echt: Sie zeigen, ob die genannten Parameter im Hilfetext der installierten Azure CLI stehen; sie beweisen nicht, dass etwas im Mandanten funktioniert.
- TOTP ist hier echt gerechnet (HMAC-SHA-1, 6 oder 8 Stellen, 30 Sekunden); die Authentifizierungs-App und die Anmeldung von Entra ID sind nicht beteiligt. Wiederverwendungsschutz und Sperrung nach Fehlversuchen bildet das Modell nicht ab.

## Musterlösung

<details>
<summary>Antworten und Zielzustand (erst nach dem Versuch öffnen)</summary>

1. Siehe `beispiele/mfa.ausgabe.txt`: Parameter für `az rest` vorhanden; Richtlinien setzt man im echten Entra ID über Graph, hier nicht ausgeführt.
2. Selbsttest: Alle sechs Zeiten (59 bis 20000000000) ergeben genau die Werte der RFC 6238 (z. B. 94287082 bei Zeit 59): die Berechnung ist richtig.
3. Mit dem Geheimnis `JBSWY3DPEHPK3PXP`: Zeit 1000 → 475209 (Schritt 33); 1029 und 1030 → 992976 (Schritt 34); 1059 und 1060 → 977407 (Schritt 35).
4. Code 475209: Zeit 1000 angenommen; Zeit 1030 ohne Fenster abgelehnt; mit Fenster ±1 angenommen (Abweichung −1); Zeit 1090 auch mit Fenster ±1 abgelehnt.
5. Lizenzstand (Auszug, 20.11.2026): Sicherheitsstandards für alle Kunden; Bedingter Zugriff erfordert P1; risikobasierte Richtlinien erfordern P2.

**Kontrollfragen (Antwortskizzen):**

1. Die Berechnung stimmt mit allen sechs Testwerten der RFC 6238 überein (SHA-1, 8 Stellen).
2. Alle 30 Sekunden (Schritt 33 bei Zeit 1000, Schritt 34 bei 1029, Schritt 35 bei 1059).
3. Der Server rechnet im Schritt 34; der Code stammt aus Schritt 33.
4. Entra ID P1 (Microsoft Learn, Suchauszug 20.11.2026).
